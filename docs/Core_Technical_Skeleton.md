# Backlog Breaker：Steam「游戏荒终结者」项目方案

> **英文全称**：Backlog Breaker — A Context-Aware & Knowledge-Graph-Based Steam Game Recommender
> **文档类型**：Project Proposal / 技术骨架（统一推荐主干；多人增加开局检查与群体排序）

---

## 1. 项目概述

玩家选不出游戏，常常不是没有游戏，而是找不到同时满足“这个人（这群人）、这种玩法（在线 / 同屏）、这份预算”的那一款。本项目面向 Steam PC 平台，构建上下文感知的游戏推荐系统，解决两件事：

1. **找下一款**：给出“想要这种感觉”的下一款，并说明像在哪、差在哪；
2. **一起玩**：在满足全员开局条件的游戏中，按每个人的喜好做群体排序，并附上开局方案（模式、谁买谁免、步骤）。

两个场景共用一条推荐主干：理解要求 → 检查硬条件 → 多路找候选 → 计算个人喜好分 → 排序与重排 → 带证据的卡片。多人请求在这条主干上增加两项：开局条件检查，以及把个人喜好分合成群体分。满足人数、开局方式、预算等条件之后，仍要从可玩的游戏中选出大家更想玩的几款。

**数据原则**：全部事实取自可程序化获取的公开数据（Steam 商店与评测接口、Steam Web API、IGDB、IsThereAnyDeal、Kaggle 公开评测数据集，见 6.3），不做逐款人工整理或核验。数据源提供不了的细节（如私人房间、键盘拆分、发行商通行证）不建模，不靠人工补齐；数据源有但某款游戏缺失的字段记 UNKNOWN。

两个场景共用标签匹配、游戏介绍匹配、同好信号、图关系召回和最终排序。价格、已有库、区域、平台与语言作为**通用约束层**生效。生成式 LLM 负责把用户要求整理成字段，以及根据事实写推荐理由；文本向量与重排模型提供喜好匹配分（精排也可由生成式 LLM 承担，但只给软偏好打分）；Python 负责约束判断、成本计算、分数聚合与最终排序。

## 2. 问题陈述

通用推荐（标签、热度、榜单）把“好不好、像不像”当作唯一问题，缺少两样东西：**使用情境约束**（几个人、在哪玩、已有什么、预算多少）和**有出处的事实**（联机模式与人数上限、核心玩法、制作血统、价格）。由此产生四类现实死局：

| 痛点                           | 典型表现                                                                                                                                           | 缺什么                                                     | 对应       |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- | ---------- |
| 通关后审美戒断                 | 打通神作后意犹未尽，想找制作水准、手感相近的作品，但标签相似不等于体验相似                                                                         | 玩家实际偏好、体验特征与制作血统                           | 场景一     |
| 复合玩法断层                   | 想要“肉鸽探索 + 基地经营”，标签共现的作品里两种玩法往往只是附带                                                                                  | 两种玩法都是核心玩法的证据                                 | 场景一     |
| 多人开局条件卡死（合作与对抗） | 5 人各自在家，却被推荐在线最多 4 人的游戏；客厅 4 人想同屏，游戏只支持 2 人分屏；异地好友想玩只有本地模式的游戏，不知道可以远程同乐 | 按模式区分的人数上限、开局方式与逐人权益核算               | 场景二     |
| 好价格与口味对不上             | 大促页按折扣或热度排序，不按个人口味；想要便宜又合心意的，只能自己一页页翻                                                                         | 个人偏好画像 + 真实史低                                    | 通用约束层 |

现有做法都不够用：商店分类只说“支持在线合作”，不说最多几人；问群友、翻攻略慢且零散；问通用 LLM 能得到像样的名单，但人数上限、开局方式等事实容易出错，也给不出出处（均需用真实请求验证，见第 7 节）。

**主张**：可行性优先。这个人（这群人）在自己的处境下真能玩，才进入推荐；相关性排序只在可行的候选里做。

## 3. 目标与范围

**目标**

1. 找下一款：给出带事实依据的推荐，说明“像在哪、差在哪”（共享核心玩法、同好信号、血统路径）。
2. 一起玩：从全员可玩的候选中推荐大家更愿意玩的游戏，附上模式、谁买谁免与开局步骤。
3. 价格与已有库作为约束与偏好生效；系统只陈述价格事实（现价、史低、差距、新增花费），不输出“该不该买”的结论。
4. 相对数据源所载事实，硬约束违例为零；缺失的事实记 UNKNOWN，不被当作支持。
5. 会话内修改条件可即时重算，无需重新开始。

**范围内**

- 平台与对象：Steam PC 上的单人与多人游戏；多人覆盖合作与对抗（在线 / 同屏 / 远程同乐 / 混合开局）。操作系统等平台信息按成员设备逐人判断，不写死为 Windows；首批数据与演示以 Windows 为主。
- 区域：价格、史低、可购买性与币种按成员的 Steam 商店区（region，如 CN、US）参数化，系统不绑定单一地区。首批数据区为 CN（人民币，文中示例的 ¥ 均指 CNY），另设对照区 US（已接入，CN、US 两区都进每日价格快照与实时查价），用于验证换区只需多灌一份价格快照；只在同一区内比较，不做汇率换算，不用别区价格回退。
- 实体：游戏、工作室、系列、玩法标签（带票数权重）、游玩模式（在线 / 同屏 / 局域网 / 远程同乐，各自的合作与对抗人数上限）、价格快照、玩家同好关系（来自公开推荐数据）。
- 判断维度：按模式区分的人数上限、开局方式（在线 / 同屏 / 远程同乐 / 混合）、购买权益（每人一份 / 远程同乐仅主机 / 免费）、内容雷区、预算、平台（含 Steam Deck 兼容等级）、语言、年龄分级。

**范围外**

- 不建模数据源不提供的开局细节：私人房间、非满员开局、入局方式、队伍结构与人机补位、键盘拆分、键鼠手柄混用、发行商通行证（如 Friend’s Pass）。这些在开局卡中统一提示“以游戏说明为准”，不做判断，也不靠人工补录。
- 不做逐款人工核验；数据源之间冲突或缺失时记 UNKNOWN，不推断为支持。
- 不从粗标签推断开局条件：“支持多人”不等于支持 5 人，人数上限以带人数的字段为准。
- 不输出“买 / 不买”这类主观裁决，不承诺“零吃灰”或“100% 满意”；不把“同工作室 / 同制作人”等同于同品质，卡片中区分事实血统与主观口碑。
- 不覆盖跨平台（Switch / PS）联机，不建模 Steam 家庭共享：前者数据源不统一，后者涉及并发与账号限制。对抗类（PvP）在范围内，按人数上限判断。
- 不强制读取私密 Steam 库（降级为问卷）；不控制本地 Steam 客户端与支付。

## 4. 使用场景

### 4.1 用户接入与冷启动

四条路径分两层，可以自由组合，不是四选一：第 1 层回答“你有什么”（A 或 B，二选一，结果相同），第 2 层回答“这次想要什么”（C、D 可同时用）。两层都可以不填，也可以都填，所有输入合成同一份 SessionSpec，后面的筛选、打分、排序完全一样。

| 路径               | 方式                                                                              | 获取内容                                                                                                                                         |
| ------------------ | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| A 官方登录（推荐） | Steam OpenID 2.0，跳转 Valve 官方页面授权                                         | 仅取 64 位 SteamID，后端用项目自己的 Web API key 调用 GetOwnedGames 拉取已购清单与时长（需要 key，官方条款为每日 10 万次）；系统不接触密码与令牌 |
| B 免授权接入       | 输入 Steam 主页链接或 Vanity ID                                                   | 解析 SteamID，读取公开库                                                                                                                         |
| C 种子问卷         | 点选 2~3 款喜欢的游戏，勾选偏好与雷区                                             | 库私密或无 Steam 账号用户的初始偏好                                                                                                              |
| D 对话提取         | 直接用自然语言描述，如“我以前沉迷《文明6》和《星露谷》，今晚想找类似的轻松游戏” | 由 Step 1 解析为偏好与约束                                                                                                                       |

- **组合时怎么合并**：
  - 第 1 层的库提供三样东西：库内锚点（权重 = 相对时长分位，见 5.5）、“已拥有 / Steam 上玩过”的排除与标注，以及多人场景的权益核算。
  - **库只用 Steam 自己的记录，不设人为时长门槛**（2026-10-14 定）。GetOwnedGames 只告诉我们两件事：拥有什么，在 Steam 上玩了多久。在别的平台、别人账号上玩过，我们无从得知，不猜：
    1. Steam 时长 > 0：Steam 记录他启动过，单人请求默认不再推荐（多人请求不按 Steam 时长排除，朋友常常愿意一起重玩；多人时只排除说过玩过、标过不喜欢或这次在卡片上点过“玩过了 / 不感兴趣”的，见 10.12 与 `rules.hard_filter`）；锚点权重直接取时长分位，玩得短分位自然接近 0（模拟中《Dead Cells》0.7 小时，分位约 0），不需要另设“几小时才算”。
    2. Steam 时长 = 0：可以推荐，卡片只陈述事实“已在你的 Steam 库里，Steam 上没有游玩记录”，不写“你没玩过”。
    3. 别处玩过的，只能由用户告诉我们：话里说的（如“Switch 上玩过《空洞骑士》”）由 Step 1 抽成“已玩过”，排除；说喜欢的同时当种子。推荐卡片上可点“玩过了”，本次会话内排除并补位。
    4. 全部游戏的时长都是 0，视为用户隐藏了游玩时间（Steam 隐私设置里可勾选“始终将总游戏时间设为私密”）：库只用于“已拥有”标注，不当口味锚点，也不按时长排除，并提示用户。
  - **实测（2026-10-14，`scripts/probe_owned_sample.py`）**：从 Kaggle 评测里随机抽 600 名评测者（每人有一条写评测时 Steam 时长 ≥ 1 小时的评测），用项目 key 查 GetOwnedGames，只统计数字：
    - 正常（有游戏、有时长）288 人（48.0%）；游戏详情不公开 290 人（48.3%，其中资料页公开但游戏详情不公开的 201 人）；有游戏但时长全 0 的 22 人（3.7%）。
    - 全 0 的 22 人里，21 人的库里列着他评测过的那款，时长 0，而评测记录他玩过 ≥ 1 小时。Steam 时长只增不减，所以全 0 就是被隐藏了，规则 4 成立；这 22 人的 playtime_2weeks 也全是 0（正常组 288 人中 235 人有）。对照：正常组列出评测游戏的 276 人，时长全部 ≥ 评测时的时长。
    - 每款游戏只返回 appid、playtime_forever、playtime_2weeks 三个字段（不是 key 主人的号拿不到最后游玩时间）。
    - 约一半用户的库读不到（游戏详情不公开），OpenID 登录也一样，因为读库用的是项目 key。库读不到时引导用户把“游戏详情”改为公开，或直接走 C / D；C、D 必须能单独给出好结果。样本是 2025 年写过评测的活跃玩家，普通用户的比例可能不同。
  - 第 2 层的 C、D 提供种子（问卷点选的游戏和话里提到的游戏都算，权重 1.0）、雷区与硬条件、feel_tags 和偏好原话。
  - 有显式种子时（2026-10-13 定），库只在“像种子的游戏”里调先后，不自己带候选进来：
    1. 只用第 2 层（种子、偏好原话、感觉标签）算个人分，取本次候选里分数最高的 50 款作为种子池。
    2. 库内锚点（权重 = 相对时长分位）另算一份库口味分，在种子池内 min-max 归一化。
    3. 种子池内：个人分 = 种子分 + 0.2 × 库口味分；池外不加分。50 与 0.2 为初始值，待请求集调节。
    这样“这次想要的”决定候选范围，“一贯玩的”只在范围内体现个人口味。依据：模拟（`scripts/simulate_inputs.py`）中，库（《文明6》300 小时、《Hades》80 小时等）+“想再找几款像《Hades》这样的，别太难，100 块以内”，原规则（库锚点 × 0.5 与种子一起算，同好通道相加）让《文明5》排到第 2（2026-10-13 的模拟），而它只按种子算排不进前 200；新规则下《文明5》出局，2026-10-16 重跑时前 5 是《暖雪》《Bastion》《Cult of the Lamb》《Death Must Die》《BlazBlue Entropy Effect》，都是像《Hades》的动作类 Rogue。
  - 没有显式种子时（只有库，或库 + 只说感觉），库内锚点照常作为口味。
  - 只有 D 的感觉描述、没有种子时，感觉通道负责“这次的感觉”。
  - 两层冲突时以第 2 层为准，例如库里最常玩恐怖游戏，但这次说“不要恐怖”。
    - **种子池与库加分的实测**（2026-10-14，`scripts/eval_ranking_groups.py bonus`，3,000 名留出评测者：最后一款好评当种子，其余当库，猜后来的好评，Recall@20）：只用种子 0.156；池 50、加分 0.2 是 0.174；加分越大、池越大，离线分越高（不限池、加分 1.0 是 0.213，旧规则“库锚点 × 0.5 一起算”是 0.204）。离线的“答案”是他后来又好评了什么，和整个库比和这一次的种子更像，所以这项测试天然偏向“库说了算”，量不出“这次想要像《Hades》的”。取舍：保留池 50、加分 0.2，已经拿到离线收益的约四成（+0.019），同时不让库把这次的要求带偏（《文明5》进“像《Hades》”的前 5 就是旧规则的结果）。
- 只做收敛推荐（2026-10-12 已定）：用户这次要什么就给什么，不处理“换换口味”“给点惊喜”这类发散请求，不为此设专门规则。
- 库设为私密时 GetOwnedGames 返回空的 response、不含 game_count 字段（社区实测；game_count = 0 是公开但没有游戏的库）：系统以“响应不含 game_count”判为私密，置 is_library_public = false，引导到路径 C，不报错。
- 多人组队可混合接入：部分成员绑定账号（自动核算已有权益与时长画像），其余成员以访客身份点选偏好；每位成员各自选择商店区（region），用于价格、史低与可购买性判断。

### 4.2 场景总览

|            | 场景一：找下一款                       | 场景二：一起玩                                                        |
| ---------- | -------------------------------------- | --------------------------------------------------------------------- |
| 用户一句话 | “刚通关《哈迪斯》，还想要类似的”     | “我们 5 个人各自在家，今晚想一起玩点合作的”                         |
| 推荐逻辑   | 检查硬条件 → 多路召回 → 个人喜好排序 | 增加开局检查 → 共用多路召回与逐人打分 → 群体喜好排序                |
| 硬约束重点 | 内容雷区、平台与语言、预算上限         | 按模式的人数上限、开局方式、逐人权益、预算上限                        |
| 交付       | 推荐卡：像在哪、差在哪、同好与血统证据 | 群体推荐卡 + 开局方案：为什么适合大家、模式、步骤、谁买谁免           |

两个场景共用 Step 1~6（见 5.1、5.3）。场景二复用场景一的候选召回与个人打分方法，在 Step 2 增加开局检查，在 Step 4 增加群体分数聚合；人数与开局方式通过后，核心仍是推荐排序。用户还可以同时提出共同偏好，如“5 人一起玩，想要像《双人成行》那样互相配合”，共同偏好与各成员画像一起参与排序（见 4.5）。

### 4.3 场景一：找下一款

**锚点：用户怎样说“想要这种感觉”**

| 锚点类型 | 用户怎么说                              | 系统如何落成锚点                                                                                                                       | 召回路径                                                                  | 交付的证据                                                       |
| -------- | --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 种子游戏 | “刚通关《哈迪斯》，还想要类似的”      | 种子 AppID → 玩法标签向量（按标签票数加权）、游戏介绍向量、同好向量                                                                   | 标签余弦 + 介绍匹配 + 同好通道 + IGDB 相似游戏 + 同工作室 / 同系列                        | 共享核心玩法、同好统计、血统路径、与种子的差异             |
| 机制组合 | “想要肉鸽探索 + 基地经营，不要换皮作” | 两个标签都须是该游戏的核心标签（票数占比达到阈值），再用组合描述（如“探索获得资源，回来建设基地”）匹配介绍 | 核心标签交集 + 组合描述的介绍匹配（有偏好原话时精排）                     | 两个核心标签的票数占比 + 介绍中对应的原句                        |
| 偏好描述 | “想玩点轻松的，不用动脑”              | LLM 从 Steam 标签清单（446 个，带中文名）选出想要 / 不想要的感觉标签（feel_tags），经 Pydantic 校验；同时保留原话匹配游戏介绍            | 感觉通道（想要的标签加分、不想要的减分）+ 游戏介绍匹配                    | 命中的感觉标签（玩家投票）与介绍中的对应描述                     |
| 库画像   | “从便宜的里面挑几款我可能喜欢的”      | 按相对游玩时长（比该游戏其他玩家玩得多的程度，见 5.5）取库内代表作，作为多个锚点（多兴趣画像），标签、介绍与同好三路分别计算          | 对各锚点相似度加权求和（离线评估中相加好于取最大值，见 5.5）+ 价格偏好    | 与最相近的那款已玩游戏的共享玩法                                 |

没有显式锚点时，默认以库画像为锚点；库也没有则触发冷启动问卷（4.1）。“库画像 + 价格偏好”即大促淘金：从合口味的游戏里挑出便宜或接近史低的。

**处理逻辑**

1. **需求理解**：LLM 把用户要求填入 SessionSpec，只填用户说过的字段，并保留偏好句段供游戏介绍匹配；种子游戏经 AppID 与别名表对齐（中英文商店名 + LLM 整理的中国玩家常用叫法，2026-10-14 建成，见 Data_Sources.md ①），对不上就向用户确认，不猜。一个叫法对应多款时（145 个，多为同一游戏的不同版本）先取评价数最多的一款，并在结果页写明“按《X》理解，另有 N 个版本”，用户可以改。
2. **硬筛（轻）**：内容雷区、平台与语言、年龄分级、预算上限（仅用户明说才设）；Steam 记录玩过（时长 > 0）和用户说玩过的游戏默认排除（规则见 4.1）。UNKNOWN 保留并标注。
3. **多路召回**：标签通道（标签余弦）+ 游戏介绍通道（文本向量匹配）+ 同好通道（公开推荐数据的物品协同）+ 血统通道（同工作室 / 系列，保留路径）+ IGDB 相似游戏（集合型特征）；独立通道可并行，各通道分数归一化后加权融合（RRF 作对照），保留各路来源。
4. **个人打分**：标签、游戏介绍、同好与血统特征共同计算喜好分；有偏好原话或感觉标签时，对靠前的一批候选用精排器（现行为生成式 LLM，见 5.5）进一步比较原话与游戏介绍。模型只评估偏好匹配，硬条件继续由规则检查。
5. **排序与重排**：只在与当前最高喜好分相差不超过 δ 的候选之间（相关性窗口），用口碑、价格偏好调整，再用 MMR 取 Top 3~5；固定加权排序保留为对照，公式见 5.5。
6. **证据卡**：由确定性事实拼装，LLM 只写 60~120 字的理由。

**交付：推荐卡（示意，具体标签与数值以知识库为准）**

```text
【推荐 1】《Transistor》
像在哪    共享核心玩法：动作、构筑成长（Steam 标签）
同好      推荐《哈迪斯》的玩家中 xx% 也推荐本作（公开推荐数据统计）                〔事实〕
血统路径  《哈迪斯》 → Supergiant Games → 《Transistor》（同工作室，DEVELOPED_BY）  〔事实〕
差在哪    缺少“类 Rogue”，多出“策略”（取自标签向量差值，非主观评价）
口碑      好评率 xx%（贝叶斯平滑后）                                              〔主观，单列〕
价格      现价 ¥xx ／ 史低 ¥xx ／ 距史低 xx%                                    〔事实，仅陈述〕
库状态    未拥有
```

**回退与边界**

- 种子不在知识库：提示“未收录”，请用户确认或改用问卷，不用相近名字硬配。
- 机制组合找不到两个标签都是核心标签的游戏：降级为“一个核心、一个次要”的候选，卡片标注“其中一种玩法是次要元素”。
- 候选不足：先放松软偏好（如同工作室），再放松价格偏好；硬约束不放松（规则见 5.5）。
- 血统是事实路径，口碑是主观评价，卡片中分开呈现。

**交互**：用户说“再轻松点”“别要恐怖的”“只看 ¥80 以内”，系统在 SessionSpec 上就地打补丁，按改动字段决定从哪一步重算（软偏好从 Step 3，雷区与预算从 Step 2）。

### 4.4 场景二：一起玩

场景二继续使用相同的推荐主干。开局检查先排除玩不了的游戏；剩余候选使用与单人相同的个人打分方法，再合成群体分数，挑出大家更愿意玩的游戏。

**输入**：成员列表（已绑定账号的成员读取已有库，访客只填偏好与雷区；每人的平台与商店区）、场地分组（谁和谁在同一台机器 / 同一块屏幕前）、互动类型 interaction（coop / versus / any）、预算（每人上限或团队总额）。开局方式 setup_type 由场地分组推出，不要求用户单选。访客默认按“未拥有”核算，可在卡片上勾选已有。

**开局方式（由场地分组推出）**

模式是否存在看 Steam 官方分类，人数上限看 IGDB 的 multiplayer_modes（取 PC 平台那一条）。

| 开局方式          | 适用                                             | Step 2 可行性检查                                                                                         | 权益与成本                                       | 开局卡内容                                   |
| ----------------- | ------------------------------------------------ | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------ | -------------------------------------------- |
| 在线组队 online   | 各自在家，每人一台电脑                           | 有在线合作 / 在线 PvP 分类；人数 ≤ onlinecoopmax（合作）或 onlinemax（对抗）                              | 每人一份；免费游戏为 0                           | 通用联机步骤（房主建房、好友邀请）、谁买谁免 |
| 本地同屏 local    | 同一屏幕                                         | 有同屏 / 分屏分类；人数 ≤ offlinecoopmax（合作）或 offlinemax（对抗）                                     | 一台机器一份                                     | 控制器支持等级、谁需要买                     |
| 混合开局 hybrid   | 部分成员同屏、其余在线（如 2 人客厅 + 3 人在线） | IGDB 标注 splitscreenonline；总人数 ≤ 在线上限；每台机器的同机人数 ≤ 同屏上限                             | 每台机器一份                                     | 每台机器的人员 + 通用联机步骤                |
| 远程同乐 remote   | 人在各地，游戏只有本地多人模式                   | 有远程同乐分类（Remote Play Together，id 44）；人数 ≤ 同屏上限                                            | 仅主机需拥有（Steam 远程同乐的通用规则）         | 谁当主机、来宾如何加入                       |

远程同乐把只有本地模式的游戏放回异地组的候选池，并能把购买压到一人出钱，甚至零成本。

四种方式共用同一个模型：把成员分到若干台机器上（场地分组），同一台机器上的玩家共享一份权益，机器之间走联网规则；远程同乐是“来宾在别处、玩家位在主机上”的特例。

**判定规则**：缺少对应分类 → FAIL（该模式不存在）；IGDB 有人数而 Steam 无对应分类 → UNKNOWN（两源冲突）；有分类且人数不超上限 → PASS。有分类但 IGDB 缺人数时，依次用三条补充规则（见 10.2）：2 人请求直接 PASS；商店介绍中写明的人数（只用于判 PASS，超过时记 UNKNOWN）；“大型多人”标签在 10 人以内判 PASS；仍无法判断则 UNKNOWN。

**处理逻辑**

1. **粗召回**：用 Steam 官方分类圈出候选池，按 interaction 选取（在线合作 38 / 在线 PvP 36、同屏合作 39 / 同屏 PvP 37、局域网、远程同乐 44 等；分类 id 以商店返回为准）。
2. **模式与人数检查**：按上表逐款判定 PASS / FAIL / UNKNOWN；任一成员的雷区、平台、语言不满足则 FAIL。
3. **权益与最低成本方案**：按权益规则（每人一份 / 每台机器一份 / 远程同乐仅主机 / 免费，见 5.5）求总花费最小的购买方案；再按预算校验，超出则 FAIL（原因记为预算）。
4. **共用召回与群体排序**：复用 4.3 的标签、游戏介绍、同好与血统通道。分别给每位有偏好的成员计算个人分，形成“成员 × 游戏”的分数表；各成员分数先在候选池内归一化，使彼此可比，再用 0.6 平均 + 0.4 最低分合成群体分；Nash 分数乘积作为首要对照算法。带共同锚点或偏好描述时，同时计算共同要求匹配分。随后使用与单人相同的相关性窗口、窗口内口碑 / 价格调整与 MMR，输出 Top 3~5。候选数量较小时，对全部已通过检查的游戏先批量算个人分，再选取一批做语义精排。
5. **开局卡**：确定性事实 + 按开局方式的通用步骤模板，LLM 仅润色理由；私人房间、入局方式、控制器分配等未建模细节统一提示“以游戏说明为准”。

**含 UNKNOWN 的候选**：单独放进“待确认”组（最多 2 款），写明缺哪项事实（如“IGDB 未收录在线人数上限”），不占 Top-K（2026-10-14 定）。

**交付：开局卡（示意）**

```text
— 在线组队 · 5 人 —
【推荐 1】《某游戏 X》  在线合作 · 最多 6 人
开局步骤  ① 房主开启游戏并建房  ② 通过 Steam 好友邀请其余 4 人  ③ 房间与入局细节以游戏说明为准
谁买谁免  小张、小李已有；小王、小赵、小陈各付 ¥38（预算内），团队新增 ¥114
价格事实  现价 ¥38 ／ 史低 ¥38（已在史低）
来源      模式：Steam 官方分类；人数：IGDB multiplayer_modes；价格：Steam / ITAD，取数于 20xx-xx-xx
未通过    《某游戏 Y》在线合作最多 4 人，差 1 个位

— 本地同屏 · 4 人 —
```

**无解时**：冲突分析器（5.5）给出最小代价的松绑方案，如“预算增至 ¥X，则 k 款可用”“改用远程同乐，则 k 款可用”“少 1 人，则 k 款可用”“接受待确认的游戏，则 k 款可用”；内容雷区不作为松绑对象。

**交互**：“把预算改成每人 ¥80”“小张晕 3D”“改成客厅 4 个人”，按改动字段就地重算；切换开局方式时停用不适用的检查（如改为 local 后不再核算每人一份）。

### 4.5 组合场景示例

> 我们 5 个人各自在家。想找类似《双人成行》的配合解谜感，同工作室的也行；经营有一点就好；每人预算最多 ¥50，尽量接近史低；谁库里已有就不用再花钱，优先看。

1. **需求理解**：SessionSpec：成员 5 人（部分已绑定账号，全员 region = CN），sites = 5 个单人场地组（推出 setup_type = online）；anchor = 种子《双人成行》；budget = ¥50 / 人；price_intent = near_record_low；library_policy = prefer_owned；同工作室、经营为软偏好。
2. **硬筛（场景二）**：只保留有在线合作分类、且在线合作人数上限 ≥ 5 的游戏，其余 FAIL；人数上限缺失的进“待确认”。
3. **共用召回与个人打分**：沿 DEVELOPED_BY 找同工作室作品，同时按标签、介绍与同好通道找需要互相配合的游戏；同工作室作品若全部因人数被排除（《双人成行》本身只支持 2 人），其余通道继续从已通过检查的候选中找游戏。分别用每位成员的种子、问卷或库画像打分，共同要求“配合解谜、轻度经营”另算一个匹配分。
4. **群体排序与重排**：先合成 5 人的群体分，再结合共同要求匹配分；在相关性窗口内用口碑与接近史低程度调整，MMR 避免候选过于相似。购买方案与每人预算在硬筛时检查，价格便宜不能让明显不合口味的游戏越过窗口上升。
5. **输出与反馈**：开局卡 + 购买清单；用户可继续改条件（如预算改为 ¥80），按改动字段就地重算。

模式切换：用户改口“改成 4 个人在客厅连电视”→ sites 改为 1 个 4 人场地组（推出 setup_type = local）：改查同屏分类与同屏人数上限，权益改为一台机器一份，输出本地同屏开局卡。

### 4.6 通用约束层：价格、已有库、区域、平台与语言

对两个场景同时生效，不单独构成推荐场景。

**价格时效：快照粗筛，实时定稿**

现价随促销随时变化；史低只在出现更低价时才变，但大促当天也会刷新。全库每次请求都实时查不必要，只对最后入围的少数游戏实时查：

1. **每日快照**：全库 7,304 款的现价与史低每天刷新一次（Steam 批量接口每区约 75 次请求，ITAD storelow 每区约 37 次），只用于 Step 2 的预算粗筛，以及没有价格诉求时的价格展示兜底。
2. **实时定稿**：Step 4 先按喜好分取前 N 款入围（默认 N = 20），对入围游戏按成员所在区实时查一次 Steam 现价和 ITAD 史低（每区各 1 次批量请求，并发执行，超时 3 秒）。预算复核、价格偏好、新增花费与卡片展示都以实时值为准；复核不通过的游戏移出，由后面的入围游戏递补。同一 (游戏, 区) 的实时结果缓存 10 分钟。
3. **结果页筛选**：卡片展示 Top 3~5，其余入围游戏作为备选保留在结果页；用户可按实时价格、是否打折、是否接近史低自行筛选，筛选只在入围列表内重排，不重跑 Step 1~3。
4. **兜底**：实时查询失败时使用每日快照，卡片注明“价格取于 yyyy-mm-dd”。

不把预算整体移到推荐之后：用户明说了预算（如“每人 ¥50 以内”）时，若推荐阶段不管预算，Top 3~5 可能全部超预算，事后筛选会筛空；多人场景的“谁要买、每人花多少”也依赖权益核算，用户无法自己筛。用户没说预算时，价格本来就不参与推荐，只在卡片上陈述，与“推荐后再看价格”等价。

## 5. 系统设计

### 5.1 总体架构

```text
用户要求 / 界面交互
        │
Step 1  需求理解 ──────────► SessionSpec + 保留偏好句段
        │
Step 2  硬条件检查 ◄──────── 知识库与每日价格快照
        │ └─ 多人分支：模式 / 人数上限 / 权益
        │ 已通过的游戏 + 对应开局方案
Step 3  多路召回与逐人打分 ◄ 标签 / 游戏介绍 / 同好 / 图关系 / 成员画像
        │ 独立通道并行 → 分数融合 → 小候选集语义精排（有偏好原话或感觉标签时）
        │ 个人分数表 + 共同要求匹配分
Step 4  统一排序与重排 ◄──── 入围 Top-20 的实时现价与史低
        │ 单人用个人分；多人先归一化、再合成群体分
        │ 取入围 Top-20 → 实时价格复核预算 → 相关性窗口 → 窗口内口碑 / 价格调整 → MMR
        │ Top 3~5 + 备选（结果页可按价格筛选）
Step 5  证据说明 ◄────────── 图谱路径 / 介绍原文 / 硬事实
        │ 推荐卡；多人卡片附开局方案
Step 6  双层反馈 ──► 快循环：修改条件，回到 Step 1
                 └─► 慢循环：沉淀偏好，写回成员画像
```

技术栈：Python · NumPy / SciPy · PostgreSQL 16 · Pydantic v2 · LLM 结构化输出 · 预训练多语言文本向量与重排模型；后端 FastAPI，前端 React + Vite + TypeScript（界面原型见 `design/prototype.html`）。模型不限定本地部署：生成式 LLM 默认调用 API 服务，向量与重排模型可本地部署或调用 API，按质量、耗时与成本选择（各模型使用点见 5.2）。游戏介绍向量离线生成，首批规模用 NumPy 矩阵检索；各路召回与外部数据请求按依赖关系异步并发。

**部署**：应用跑在带 GPU 的本机上（向量模型在本机）。`scripts/serve.ps1` 先启动 Docker 与 PostgreSQL 容器，再以 `--host 0.0.0.0 --port 8000 --proxy-headers` 启动 uvicorn，供另一台服务器上的反向代理经私有子网访问（`--proxy-headers` 让 Steam 登录回跳到公开地址，而不是本机地址）。反向代理负责 HTTPS、basic auth，并对 `/api/recommend`、`/api/followup`、`/api/reasons` 设一条共用的限速（每分钟 6 次），代理超时 180 秒。应用本身仍没有认证，只能经这样的代理对外开放。

### 5.2 设计原则

1. **权力边界**：生成式 LLM 整理需求、写解释，并可作为可选的精排器；文本向量和重排模型（或担任精排器的 LLM）只提供软偏好匹配分；模式、人数、权益、预算、分数聚合与最终排序由 Python 执行，模型输出不作为任何硬事实的依据。
2. **硬约束与软偏好分离**：模式、人数上限、雷区、预算上限一票否决；风格、同工作室、折扣高低只加分，不做硬排除。
3. **三值逻辑**：每项事实只有 PASS / FAIL / UNKNOWN；UNKNOWN 保留并标注“需自行确认”，绝不视同通过。每条事实记录来源与取数时间。
4. **全员可用**：联机核算每个人是否需要购买，不把“团队有人拥有”等同于“全员免费”，购买按权益规则核算。
5. **只用可获取的数据**：判断维度以公开数据源能提供的字段为界；数据源没有的细节不建模，不靠人工补录。
6. **价格只陈述事实**：系统给出现价、史低与新增花费，不替用户判断值不值得买。
7. **无解不乱推**：候选为空时给出最小代价的松绑建议，不偷换条件强行推荐。
8. **喜好主导排序**：先区分喜好匹配程度，只在喜好分相近（差距不超过 δ）的候选之间调整口碑与价格；多人先计算每个人的分数，归一化后再聚合，保留成员间的偏好差异。

**模型使用点**：全系统只需一个生成式 LLM 与一个文本向量模型；专用重排模型为可选的第三个模型。

### 5.5 关键算法

**权益最低成本方案（场景二）**

权益规则只取不依赖逐款资料的通用规则，由开局方式与 Steam 的 is_free 字段决定，不建逐款规则表：

- per_player（在线组队）：需要份数 = 玩家数；新购份数 = 未拥有者数；
- per_machine（本地同屏、混合开局的每台机器）：同一台机器上有一人拥有即可用，新购份数 = 没有拥有者的机器数；
- host_only（远程同乐）：只有主机需要拥有，来宾不计；新购份数 = 主机未拥有时为 1，主机可在拥有者中任选，因此有人拥有即为 0；
- free（is_free = true）：新购份数 = 0。

发行商通行证（如 Friend’s Pass）没有可程序化获取的数据源，不建模，统一按 per_player 计；卡片在该游戏的介绍提到“好友通行证 / Friend’s Pass”时附一句“可能有好友通行证，以商店页为准”，只作提示，不改变花费计算。

预算按“每人上限”或“团队总额”校验；超出则该配置 FAIL，原因记为预算。

**多区组队**：价格与预算均取各成员本区本币，不做汇率换算。全员同区时自动取总花费最小的方案；跨区时不跨币种求和，而是列出各可行方案及每人的本币花费，由用户选择（远程同乐的主机份由谁来买，价格会因所在区而不同）。

**开局方式的选择**：场地分组固定时开局方式唯一；用户只说“我们 5 个人”而未说在哪时，对 online、remote 两种异地方式分别检查，同一款游戏取新增花费最低的可行方式，卡片注明所用方式。

**共用多路召回：标签、游戏介绍、同好与图关系**

召回与个人打分对单人、多人使用同一套方法，范围限定在 Step 2 已通过的游戏内：

- **多兴趣画像**：每位成员的画像是一组锚点游戏（种子、问卷点选的游戏、按相对游玩时长取的库内代表作），不平均成一个向量。三路都对各锚点加权求和：同好通道按 EASE 相加（离线评估中相加明显好于取最大值，见同好通道）；标签与介绍通道在 2026-10-14 的融合评估中同样是相加好于取最大值（`config.TAG_AGG` / `DESC_AGG`）。卡片上的“像你玩过的哪一款”取贡献最大的那个锚点。种子与问卷权重 1.0，库内锚点权重 = 相对时长分位；同时有显式种子时，库内锚点不进这组画像，只在种子池内加分（见 4.1 组合规则）。
- **相对游玩时长**：库内游戏的权重不看绝对小时数，看“比这款游戏的其他玩家玩得多还是少”：用户时长在该游戏全部评测者时长分布中的分位（0~1）。例如《双人成行》评测者的中位时长 19.4 小时、《文明6》157 小时，玩《双人成行》40 小时与玩《文明6》300 小时的分位相近。参照分布取自同好通道的评测数据（每条评测附带的 playtime_forever，正负评测都算，只用非测试评测者，每款至少 50 人），增量补抓后新游戏也有；仍没有参照分布的核心库游戏退回 log(1+时长) 在本人库内的分位（2026-10-16 实现）。不设最低时长门槛（4.1 已定）：玩得短的分位自然接近 0。依据（2026-10-13，评测总表）：在 685 万名同时有好评和差评的训练评测者里，把各人评测过的游戏按时长信号排序，看好评游戏排在差评游戏前面的概率（个人内 AUC，0.5 等于瞎猜）：分位 0.638，绝对时长 0.594（差值 0.044，95% CI [0.0442, 0.0447]）；“时长 ÷ 该游戏中位时长”0.639，和分位几乎一样，分位落在 0~1 之间，直接当权重更方便；分位与本人库内排位各半混合反而降到 0.610。脚本 `scripts/playtime_signal.py`；旧 Kaggle 2024 数据上是 0.624 对 0.584，结论相同。两者都只是弱信号，所以种子与问卷优先于库画像。并记下命中的锚点供卡片说明“像你玩过的哪一款”。平均画像会把《文明6》+《星露谷》这类不同兴趣折中成两头都不像的中间态；多兴趣表示参考 PinnerSage（Pal 等，KDD 2020）。单一加权平均画像保留为对照。
- **标签通道**：每款游戏的玩法 / 题材 / 氛围标签取自 Steam 用户标签（每款最多 20 个，带票数）。标签权重 = 该标签票数 ÷ 该游戏最高票数，再乘 IDF 降低常见标签（如“独立”）的区分权重；权重占比不低于阈值（默认 0.5）的标签记为核心标签。候选与各锚点做加权余弦匹配；同一向量定义用于召回、个人打分与 MMR。IGDB 的类型、主题、关键词与 Steam 标签重复，不再使用。
- **同好通道**：回答“喜欢这些游戏的人还喜欢什么”，只看玩家行为，补上“玩家觉得像、标签却不像”的关系。好评即推荐，差评不进矩阵，每条好评一律记 1。
  - **数据**（2026-10-13 定并建成）：评测总表 = Kaggle “steam-reviews-100m”（sergiodelcarpio，MIT，2025-08 抓取，ID 完整，8,460 万条）+ Steam 评测接口补抓的 7,693 万条（见 6.3 第 6 个来源），按评测编号去重后 1.61 亿条、5,232 万名评测者、7,412 款游戏，评测时间 2010-10 至 2026-10-13。补抓的部分：2025-08-26 以后的全部评测；Kaggle 评测文件里没有的 738 款游戏的历史；Kaggle 没有的非 Steam 购买评测（激活码、免费游戏玩家等，4,150 万条，约占三成）；Kaggle 抓漏的 179 款游戏（补到与 Steam 的条数吻合）。两边都有的 51 万条评测者编号 100% 一致，同一个人跨年份的评测天然连在一起。评测者 ID 读入即加盐哈希，派生文件不保存原始 ID。数据细节见 Data_Sources.md ⑤⑥。
  - **打分**：用 EASE（Steck，WWW 2019）。先由训练评测者的“人 × 游戏”好评矩阵 X 离线求一个 B = I − P·diagMat(1 / diag(P))，其中 P = (XᵀX + λI)⁻¹，λ 初始 10,000，并把 B 的对角线置 0。请求时，候选 g 的同好分 = Σ锚点 a 锚点权重(a) × B[a, g]：多个锚点自然相加，不取最大值。每个锚点贡献多少分可以单独拆出来，卡片据此说明“主要因为你玩过哪一款”。
  - **卡片上的统计**：另存一张两两余弦表，余弦 = 共同推荐人数 ÷ √(两款各自的推荐人数之积)，共同推荐少于 5 人不计，每款 Top-200，用来写“x 人同时推荐两款”。
  - **依据**（2026-10-13 离线评估，评测总表，5 万名留出评测者，前 20 名猜中留出好评的比例，`scripts/eval_ease.py`）：只推热门 0.149，余弦取最大值 0.168，余弦相加 0.198，EASE 0.222（比余弦取最大值高 0.054，95% CI [0.052, 0.055]）；去掉最热门的 100 款后分别为 0.057、0.130、0.151、0.172。λ 在 1,000 到 50,000 之间结果几乎不变，取 10,000。此前在 Kaggle 2024 数据上是 0.166 / 0.170 / 0.193 / 0.208，结论相同。
  - **试过、不采用的做法**：按游玩时长给好评加权，结果几乎不变（0.208 对 0.210）；Steam 商店的“更多类似内容”列表，单用只有 0.118，比只推热门（0.197）还差，与 EASE 混用也会拉低结果（两项都在旧 Kaggle 2024 数据上测，脚本与数据已删）。
  - **覆盖**：按有 ≥ 20 个同好邻居计，7,304 款里 7,303 款达到（剔除非游戏前是 7,413 款里 7,407 款），2023 到 2026 年发售的游戏全部达到（旧 Kaggle 2024 数据上 2024 年只有 53%、2025 年 35%）。缺同好数据的游戏按可用通道重新归一化权重；IGDB 相似游戏不再顶替同好打分（血统一路权重为 0，见下方融合权重），只写进卡片证据。
  - **文件**：`data/derived/ease_reviews100m.npz`（EASE 权重）、`colike_reviews100m.parquet`（卡片统计）、`playtime_reference_100m.parquet`（时长参照）、`eval_reviews100m_test.parquet`（测试评测者），由 `scripts/build_reviews_merged.py` 与 `scripts/build_review_tables.py` 生成。

- **IGDB 相似游戏**：IGDB 的 similar_games 作为集合型特征（在列表中记 1），不单独召回；与工作室、系列一起归入血统一路，离线评估后不参与打分，只作卡片证据。
- **游戏介绍通道**：清理官方游戏介绍与玩法说明，离线生成文本向量。用户偏好句段直接匹配介绍；种子与库内锚点使用同一组锚点，候选与各锚点介绍向量相似度加权求和。例如，同样带“肉鸽”标签，还可根据介绍区分紧张战斗与慢节奏思考。
  - **正式向量（2026-10-14）**：`scripts/build_desc_embeddings.py`，Qwen3-Embedding-4B fp16，文本 = 简短介绍 + 全文，中英文两版分别编码，每段最多 1,024 个 token（英文中位 389、90% 分位 743，约 3% 被截断），存 `data/derived/desc_emb_qwen3_4b.npz`（英文 7,302 款、中文 7,301 款）。本机 RTX 4070 Ti SUPER 上两版共约 20 分钟；按 (appid, 文本哈希) 缓存，名单或介绍变了只补编码变化的部分。相似度取两版中较大的：锚点对候选为“英文对英文”与“中文对中文”取大，用户原话对候选为原话对两版取大。同一款游戏中英文两版的向量相似度约 0.73（《Hades》），说明跨语言可比。
- **感觉通道**（feel_tags 非空时）：“轻松点”“别太难”“想要刺激的”这类话，由 Step 1 的 LLM 映射成 want / avoid 两组 Steam 标签（只能从 446 个标签里选，Pydantic 校验标签 ID）。Steam 有一批玩家投票的感觉类标签，如放松、休闲、温馨惬意、治愈系、可爱、低容错、类魂系列，核心库中以“放松”为核心标签的有 417 款，“低容错”407 款。打分：Feel(g) = mean_{t∈want} w_g(t) − mean_{t∈avoid} w_g(t)，w_g(t) 为该标签在这款游戏上的票数 ÷ 最高票数，没有该标签记 0；只有一组时另一项取 0。与其他通道一样做池内 min-max 归一化后进入凸组合，初始权重 0.25，其余通道按原比例缩到 0.75；feel_tags 为空时不启用，权重回到原值。只加减分、不排除：带“低容错”的游戏仍可入选，只是排后。卡片“像在哪”列出命中的 want 标签。用标签而不只靠介绍向量的原因：2026-10 的演示中，“想玩点轻松的”与 7,170 款介绍的向量相似度集中在 0.31~0.38，几乎拉不开差距（`scripts/demo_walkthrough.py`）；标签是玩家投票，区分度高且能直接写进卡片。偏好原话仍走介绍通道与可选的语义精排，处理标签表达不了的细节。
- **血统通道**（有种子时）：沿 DEVELOPED_BY / IN_SERIES 找游戏，保留事实路径。工作室取 IGDB 的公司 ID（避免同一公司的不同写法被当成两家，缺失时用 Steam 的开发商名称），系列取 IGDB 的 collections / franchises。导演 / 设计师路径首版不做：唯一的程序化来源 Wikidata 全库只有约 770 款有记录。
- **机制组合**（有机制组合时）：要求所需标签均为该游戏的核心标签；再把组合写成一句描述，走介绍通道与精排，取介绍中最相关的原句作为证据。不再建玩法闭环图，因为闭环边没有可程序化获取的数据源。
- **融合权重的实测结论**（2026-10-14 定，`scripts/eval_fusion.py`，同一批留出评测者：开发 8,000 人调权重，另 12,000 人报告，Recall@20 带 95% CI）：
  - 只用同好通道最好：库画像 0.216，单个种子 0.181，两个种子 0.205。原设计权重（标签 0.30、介绍 0.25、同好 0.30、血统 0.15）只有 0.112 / 0.082 / 0.098，约为一半。
  - 标签、介绍单独用都只有 0.03~0.05；加进来只会降分：标签 + 介绍合计 0.10 时库画像降 0.0014、单种子降 0.0048，0.30 时降 0.015 / 0.031。血统作为打分项在每个权重下都降分（0.05 就降 0.003）。
  - 换归一化方法（池内分位、z 分数）没有更好；名次融合 RRF 只有 0.10（比同好单独低 0.11），不用。多锚点时“相加”比“取最大值”好。
  - 定下的权重：同好 0.90、标签 0.05、介绍 0.05、血统 0（标签、介绍两路相加）。标签与介绍保留一点，是为了同分时有内容信号、没有同好数据的游戏也能排上，代价不到 0.005。血统不再打分，只写进卡片作证据；用户明说“同工作室也行”时血统权重设 0.15。偏好原话（介绍匹配）和感觉标签各自作为独立的一份（各 0.25）叠加，因为离线数据里没有“这次想要什么”，量不出它们的作用，由请求集检验。
  - 局限：留出部分是“后来又好评了什么”，偏向同好信号，测不出“这次想要的感觉”。所以内容通道在离线评估里吃亏是预期之内的，这也是保留精排和请求集的原因。
- **分数融合**：当前规模下，每条通道都能给全部已通过的游戏打分，因此直接融合分数，不按名次合并。标签、介绍、同好三路分数在本次候选池内做 min-max 归一化；血统、IGDB 相似游戏这类集合型通道作为特征进入（同工作室 / 同系列 / 在相似列表中记 1）；按凸组合（权重和为 1）得到精排前的个人分。同一个分数既用来选进入精排的 Top-N，也是精排后融合的基础，避免“候选池按名次选、最终按分数排”两套口径。后续的相关性窗口与群体聚合都依赖分数差距，名次融合会丢掉这部分信息。

```text
精排前个人分  PreScore_i(g) = Σ通道 c  w_c × norm(s_c,i(g))，Σ w_c = 1
              norm 为本次候选池内的 min-max 归一化；集合型通道直接取特征值
精排后个人分  有偏好原话或感觉标签且进入精排：(1 − w_r) × PreScore_i(g) + w_r × norm(Rerank_i(g))
              否则等于 PreScore_i(g)
RRF 对照      RRF(g) = Σ通道 c  1 / (ρ + rank_c(g))，ρ 取原论文的 60
每个候选保留各通道的分数、名次与对应依据。
```

RRF 保留为对照：通道只返回截断名单（如规模扩大后改用近似最近邻）、分数无法校准时，名次融合更稳，届时再启用。

多人的候选来自各成员候选与共同要求候选的并集。先保留每个人的偏好，再合并候选；只用一个平均画像召回的做法作为实验对照。核心库约 7,000 款的规模下，可先对全部已通过条件的游戏批量算每个人的标签、介绍与同好分，再取各成员与共同要求的 Top-N 并集进入精排。

融合函数的选择参考 Bruch 等（ACM TOIS 2023）对混合检索融合函数的分析：归一化分数的凸组合在域内与域外均不弱于 RRF，只需少量标注即可调好权重，RRF 反而对参数敏感。RRF 原方法见 [Cormack 等，SIGIR 2009](https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf)。

**语义精排：再比较一次偏好原话与游戏介绍**

介绍通道与精排是先后两道工序，不并发。介绍通道把原话与介绍分别编码成向量，介绍向量可离线预算，一次矩阵乘即可给全部已通过的游戏打分；但整段文字压成一个向量会丢掉否定与程度，如“别太难的肉鸽”与介绍中的“极具挑战性”在向量上仍可能相近。精排同时读取原话与一款游戏的介绍，能识别这类细节，但须逐对计算、无法预算。因此介绍通道负责全量粗筛，精排只复核融合后的 Top-N。精排分也不替代精排前的个人分：精排只读文字，标签、同好与血统信息仍由精排前的个人分提供，两者按上式融合。

精排在有偏好原话或感觉标签时启用（`rerank.targets_with_words`，见 10.11）：精排器同时读取原话与候选介绍，输出匹配分；成员的个人偏好句段逐人评分，共同要求另算共同匹配分。只有种子或库画像的成员没有可供比较的原话（重排模型按“查询–文档”相关性训练，不适合比较两段游戏介绍），直接使用精排前的个人分。精排分按上式与精排前的个人分合成，融合权重 w_r 在请求集开发集调节（现为 0.9，见 7.1）。介绍缺失或模型不可用时，使用已有标签、同好与血统分，并重新归一化可用项的权重。

首版可用预训练多语言文本向量与重排模型，候选包括 Qwen3 Embedding / Reranker；用 [Retrieve &amp; Re-Rank](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html) 的两阶段方法减少逐款精排的成本，模型能力参考 [Qwen3 技术报告](https://arxiv.org/abs/2506.05176)。模型输出只用于判断喜好匹配；模式、人数、权益与预算依赖数据源字段和规则。

**精排器选型**：精排器不限定本地部署，候选两类：一是专用重排模型（如 Qwen3-Reranker，本地或 API），直接输出连续的相关性分数，稳定、可复现；二是生成式 LLM（API），对口语、长句与多条件偏好的理解更强。采用 LLM 精排时：

- **批量调用**：所有成员的偏好句段、共同要求与 Top-N 候选介绍放进同一次请求，输出完整的“成员 × 游戏”分数表，不逐款逐人调用；
- **输出与校验**：temperature 设为 0，提示词要求只返回 JSON（`{"<id>": 0~10, ...}`，多目标时外层再按目标分组），不附依据；由 `llm.chat_json` 解析，解析或校验失败时把错误附在提示后重试一次，仍失败按“模型不可用”回退（结果页注明精排暂不可用）。校验只看覆盖：`rerank.ok_one` 只收数值型的分数，缺的 id 不超过 20% 即接受，缺分的游戏按没进精排处理；没有 JSON Schema 约束，也没有 Pydantic 取值范围检查（0~10 之外的数也会进入池内 min-max 归一化）；
- **分数处理**：LLM 的离散打分较粗，同样做池内 min-max 归一化后按上式融合；若同分过多、影响相关性窗口，改为让 LLM 输出 Top-N 的完整排序，再把名次映射为分数；
- **可复现**：记录模型名、版本与调用日期，开发集与测试集在同一模型版本下跑完；
- **延迟**：精排只处理 Top-N，每次请求约增加一次调用（与 Step 5 的理由生成相当），端到端耗时按第 7 节分模块记录。

默认精排器已按第 7 节“不精排 / 专用重排模型 / LLM 精排”的三方对照定下（2026-10-16，见 7.1）：LLM 精排；Qwen3-Reranker-4B 质量明显较低，未采用。

推荐依据来自标签、同好统计、图路径与介绍原文。卡片可以引用“介绍强调两人协作解谜”，但模型的高匹配分不能作为“支持 5 人”之类硬事实的证据。

“像在哪”列共享核心标签与介绍中的对应描述；“差在哪”取候选与种子的标签权重差异中最大的 2~3 项；同好统计与血统路径直接取自同好矩阵与图查询。

**逐人打分与群体聚合**

Step 3 输出“成员 × 游戏”的分数表。每位成员的种子、问卷或库画像独立形成 UserScore。

**聚合前先让分数可比**：原始个人分的尺度随锚点类型（种子、问卷、库画像、偏好原话）和画像宽窄而不同，例如单一种子的余弦普遍偏高，宽泛画像普遍偏低。不处理时，“最低分”会总落在分数尺度最低的成员身上，而不一定是最不满意的成员；相关性窗口 δ 在不同请求间的含义也会漂移。因此每位成员的分数先在本次候选池内做 min-max 归一化（保留分数差距，供相关性窗口使用），共同要求匹配分同样处理；池内分位数归一化作为对照。Step 4 再执行聚合：

```text
S                 有个人偏好数据的成员集合
个人分            UserScore_i(g) = 成员 i 的精排后个人分在本次候选池内 min-max 归一化后的值
群体基线          GroupScore(g) = 0.6 × mean_i∈S(UserScore_i(g))
                                + 0.4 × min_i∈S(UserScore_i(g))
Nash 对照         NashScore(g) = exp(mean_i∈S(log(max(ε, UserScore_i(g)))))
共同要求          SharedMatch(g) = 共同种子、机制组合或偏好句段的匹配分（同样做池内归一化）
最终喜好分        单人：该成员的 UserScore
                  多人：GroupScore；有共同要求时，0.5 × GroupScore + 0.5 × SharedMatch
```

- **平均 + 最低分**保留为基线，兼顾整体喜好与最不喜欢的成员。
- **Nash 分数乘积**为首要对照，以几何平均和对数实现；低分成员会拉低整体分，ε 避免零分导致所有乘积为零。比较其是否提高实际群体接受度，再决定采用哪一种。积累“愿意 / 不愿意”标注后，可用 Platt 缩放把个人分校准成“愿意玩”的概率；此时乘积即“全员都愿意”的概率，与第 7 节的全员接受率直接对应，且不需要 0.6 / 0.4 这类权重。因此两者表现接近时优先 Nash。
- **合成小组实测**（2026-10-14 定，`scripts/eval_ranking_groups.py groups`）：从留出评测者里组 3 人、5 人小组，每种 1,500 组，一半随机组队，一半是“都好评过同一款游戏”的相近小组；候选限定在有在线多人分类的游戏，一款推荐对某成员算“接受”是他后来好评了它。看前 10 款里有成员接受的比例：
  - 3 人随机：平均 + 最低分 0.364，Nash 0.339，只看平均 0.370，只看最低 0.275，合并成一个画像 0.369；3 人相近：0.467 / 0.459 / 0.477 / 0.412 / 0.469。5 人结果同向。
  - “全员都接受”太稀少（随机 5 人组约 0.5%），分不出高下。
  - 结论：平均 + 最低分明显好于 Nash（3 人随机组差 0.025，置信区间不重叠）和只看最低分；只看平均略高约 0.01，但区间重叠。默认保留平均 + 最低分（0.6 / 0.4），它在不明显损失整体的前提下照顾最不满意的成员；Nash 不再作为首选，`config.GROUP_METHOD` 可切换。离线的“接受”只是“后来好评了”，真实小组的愿意 / 不愿意仍要靠请求集。
- **先比最低分、再比平均分**作为次要对照；它更照顾最不满意的成员，也更容易被一个偏好特别窄的成员左右。
- 没有个人偏好数据的成员继续参与全部硬条件检查，聚合时不补成零分。所有成员都缺少个人偏好时，用明确提出的共同要求排序；共同要求也缺失则触发种子问卷。
- 平均、最低分与乘积等聚合策略参考 Masthoff 的群体推荐综述（Recommender Systems Handbook，2011）；Nash 目标另可参考 [Multi-User Dueling Bandits，2026](https://arxiv.org/abs/2605.01961)。首版比较静态聚合目标，反馈学习在积累实际选择数据后再考虑。

**最终排序：相关性窗口、窗口内调整与 MMR**

单人与多人都使用最终喜好分 Relevance，后续排序共用以下逻辑：

0. **同系列折叠**（2026-10-13 定）：取入围 Top-20 之前，按 IGDB 的 collection（具体的系列，如“Civilization”）分组，共享任一 collection 即算同系列；franchise（如“Star Wars”“Sid Meier”“LEGO”）太宽，不用来折叠。注意 IGDB 的 collection 与 franchise 编号各自独立（collection 10 是 Dragon Age，franchise 10 是 Sid Meier），比较时要带上类型。每个系列只留喜好分最高的一款进入入围与备选，其余折叠在它下面，卡片写“同系列还有 N 款”，用户可展开。系列游戏照常可以推荐，只是不重复占位。依据：定规则时的模拟（2026-10-13）中只给库（含《文明6》）时，入围 20 款里有 7 款 Sid Meier 的游戏，备选前 4 位全是《文明》；折叠后只剩《文明5》一款，下面折叠 6 款。2026-10-16 重跑（`.cache/simulate_inputs.json`）：仍是《文明5》一款进前 5，下面折叠《文明7》《文明：太空》《文明4》3 款。没有 collection 数据的游戏（核心库 2,996 款有，约 41%）不折叠，靠 MMR 去雷同，例如《文明3 完整版》IGDB 没标系列，不会折叠到《文明》下面。
1. **口碑底线**（2026-10-14 定）：Steam 好评率低于 70%（Steam“多半好评”与“褒贬不一”的分界）或没有好评率的游戏，不进 Top 3~5，只出现在备选里，并标注“口碑褒贬不一：xx% 好评”或“暂无好评率”。只有底线以上的入围游戏选完、Top 3~5 仍凑不满时，才按原规则补入。用的是 Steam 显示给玩家的好评率，不是平滑后的口碑分，卡片说法和 Steam 页面一致。依据：口碑原本只在窗口内起作用，68% 好评的《HUMANKIND》在模拟的两条路径里都进了前 5；加底线后它退到备选第 1 位，前 5 由 82%~96% 好评的游戏补上。核心库有好评率的 7,187 款中，低于 70% 的 1,018 款（14%）。
2. 每选一款之前，以剩余候选（底线以上）中的最高喜好分 R* 为基准，只有喜好分不低于 R* − δ 的候选可以被选（相关性窗口）；δ 为可调参数。例如 δ = 0.1、R* = 0.93 时，0.87 可以在口碑与价格上与之比较，0.80 要等高于 0.90 的候选都选完后才进入窗口。
3. 在窗口内，用口碑、价格偏好与已有库偏好调整顺序。
4. MMR 每次只从窗口内选下一款；相似度与所有已选游戏比较，选满 Top 3~5 后停止。这样既保留多样性，也防止低喜好分的游戏仅因便宜或热门越过窗口上升。

窗口取代固定分档 floor(Relevance / δ)：固定分档有边界问题，0.80 与 0.79 只差 0.01 却分属两档，0.80 与 0.89 差 0.09 却同档；窗口随当前最高分移动，参数仍只有 δ。这一规则即 Tversky（1969）的词典式半序：主属性差距小于阈值时，才比较次要属性。

```text
相关性窗口 W = { g : Relevance(g) ≥ R* − δ }，R* = 剩余候选中的最高 Relevance
口碑       Quality = (好评数 + α) / (总评价数 + α + β)
价格偏好   仅有价格诉求时启用；现价与史低取入围时的实时值
           接近史低（near_record_low）：≤ 史低 × 1.05 记 1，≥ 史低 × 2 记 0，中间线性
           越便宜越好（cheap）：免费记 1，从免费到 ¥200 / $30 线性降到 0，更贵记 0
           （按第一位成员所在区取上限，config.CHEAP_ZERO）
已有优先   library_policy = prefer_owned 时启用：有成员拥有记 1，否则 0
短一点     用户要短游戏（max_hours）且 IGDB 有通关时长时启用：通关时长 ≤ max_hours 记 1，
           超出后线性下降，到 2 × max_hours 记 0
窗口内分   BaseScore = Σ w × 项值 ÷ Σ w（ranking.window_score）
           w：Relevance 0.5、Quality 0.3、价格偏好 0.2、已有优先 0.2（PREFER_OWNED_W）、短一点 0.2（SHORT_W）
           未启用的项不参与，其余权重按比例归一化（只有 Relevance 与 Quality 时：0.625 / 0.375）
MMR        在 W 内选 argmax [0.65 × BaseScore
                            − 0.35 × 与已选游戏的最大标签相似度]
```

**排序规则实测**（2026-10-14，`scripts/eval_ranking_groups.py rank`，3,000 名留出评测者，库画像路径，前 5 款的命中率 hit@5、平均好评率、列表内差异 ILD）：
- 直接取前 5：hit@5 0.104，平均好评率 87.3%，ILD 0.79，前 5 里低于 70% 好评的约占 6.5%。
- 现行规则（折叠 + 口碑底线 + δ = 0.1 窗口 + MMR 0.65）：hit@5 0.103（差别在置信区间内），平均好评率 91.3%，ILD 0.85，没有低于底线的。
- δ 越大，好评率和差异越高，命中率越低：δ = 0.2 时 0.101，全局固定加权（δ = 1）0.099。MMR 0.5~0.8 之间命中率几乎不变。
- 结论：保留 δ = 0.1、MMR 0.65。窗口和底线用几乎不损失的命中率，换来更高的口碑和更不重复的列表。

固定加权排序作为对照：直接在全部候选中按相同 BaseScore 和 MMR 排序，移除相关性窗口。两种排序用同一候选池与同一分数表比较，观察窗口是否提升个人相关性与群体接受度，以及价格偏好是否仍有效。

贝叶斯口碑的 Beta 先验 (α, β) 用全库评价数拟合（2026-10-16，`kb.fit_beta_prior`）：对 7,298 款有评测的核心游戏的好评率做矩估计，每款等权，并从方差中扣掉评测数有限带来的二项噪声，得 α = 6.69、β = 1.43（均值 0.824，先验强度 8.1；beta-binomial 最大似然给 9.4，相近）。原占位值 24.6 / 5.4 均值相同但强度约为数据支持的 3.7 倍；换成拟合值后平滑分与旧值的相关为 0.9997，按口碑排序的前 100 名不变，变化集中在评测很少的游戏上。Wilson 下界作口碑消融。MMR 继续使用 Carbonell 与 Goldstein（1998）的方法，DPP 留作低优先级备选。预算仍是硬条件，没提价格时不启用价格偏好。已有库优先作为窗口内调整，明确要求排除已有游戏时在硬筛生效。

以上参数均为初始配置；调参、群体算法选择与排序策略比较见第 7、10 节。

**冲突分析（松绑建议）**

候选为空时，对 k 个可放松的约束（k 约 10 以内）做精确的子集分析：Step 2 只跑一遍，给每个候选记一个“未通过的可放松约束”位掩码；放松约束子集 S 后可用的候选数 = 位掩码是 S 子集的候选数，用一次子集和变换（O(k·2^k)）对全部 2^k 个子集一次算完，再按“代价由低到高、可用候选数由多到少”排序。k 大到无法穷举时改用 FastDiag（Felfernig 等 2012，直接求最小松绑集，一致性检查次数约 O(d·log(n/d))）。默认放松顺序：软偏好 → 含 UNKNOWN 的“待确认”组 → 预算 → 改开局方式（如改用远程同乐） → 减少人数。预算建议值直接取“使至少 1 款通过的最小预算”，不按固定步长试探。内容雷区不作为松绑对象。

### 5.6 算法选型与并行性

规模决定选型：核心库约 7,000 款，规则过滤后候选约数百至数千款，群体不超过约 10 人，玩法标签约 100~200 维，每次请求只取 Top 3 至 5。规则与个人相似度继续使用 NumPy / SciPy；新增游戏介绍匹配与小候选集语义精排，独立召回通道可并发。优化重点是找到更合口味的候选，以及提高群体接受度。

备选方法的采用条件：

- **PPR 图传播**：同好通道已由公开推荐数据集提供交互边，PPR 在同一张“用户–游戏”图上传播，作为物品协同的对照，检验多跳关系能否补充直接共现漏掉的游戏；只在工作室、系列边上做 PPR 与血统通道高度重合，不采用。参考 [Pinterest 图推荐论文](https://arxiv.org/abs/1702.07969)。
- **矩阵分解（ALS）**：同好通道的扩展对照。EASE 已取代余弦作为同好打分（离线 Recall@20 0.222 对 0.198）；它仍是“游戏 × 游戏”的权重，每个锚点的贡献可以单独拆出来说明。ALS 只有隐向量，说不出依据，只在离线相关性明显更好时作为附加分数。
- **学习排序**：有足够的用户选择或相关性标注后，再用 LambdaMART 等学习特征权重；首版重点比较现有加权排序与相关性窗口，参考 [LightGBM 排序目标文档](https://lightgbm.readthedocs.io/en/latest/Parameters.html)。

并行执行安排：

- **独立召回通道并发**：实测（2026-10-16，`scripts/eval_extra.py latency`，`relevance` 中位耗时）不采用。一个种子 4.7 毫秒、50 个库锚点 120 毫秒、4 人小组 358 毫秒；介绍通道占通道耗时的约 90%，通道并发最多省其余 10%，实测 124 / 351 毫秒，没有更快。把 NumPy 的 BLAS 限为单线程后，小组按成员并发可从 172 降到 64 毫秒，但测时机器上还有其他任务，上线前需在空闲机器复测；相对 LLM 调用的秒级耗时，这部分不是瓶颈。CPU 中的小矩阵计算继续批量向量化。
- **模型计算批处理**：游戏介绍向量离线生成；请求时将成员偏好与候选介绍批量编码 / 精排，控制进入精排的候选量。向量与重排模型本地部署时，是否使用 GPU 根据推理耗时与部署设备确定；调用 API 时按服务商限速设置并发与超时。
- **保留数据依赖顺序**：硬筛完成后形成正式候选，召回汇合后精排，个人分完整后聚合与重排。原规则粗测为毫秒级，模型推理与外部请求单独计时，并报告端到端耗时。
- 数据灌库按主机各自限速，用异步并发（每个主机一个令牌桶）：瓶颈在对方接口的限速，不在本地算力。限速（部署前复核）：IGDB 4 次 / 秒且并发不超过 8；ITAD 文档写 1,000 次 / 5 分钟，实测连续批量请求会触发 429，需间隔约 1 秒并在 429 后等待；Steam 商店接口未见官方数字，批量接口每次 100 款，需求量很小；评测接口按 1 次 / 秒抓取未触发限流。
- 离线网格搜索可以并行，但按上述规模全程不到 1 s，网格扩大约 10 倍以上才值得。
- 松绑诊断有并行版本（并行 QuickXplain：Vidal 等 2021；FastDiagP：Le 等 2023），后者报告 8 核最好仅提速约 1.3 至 1.7 倍，不采用。

### 6.2 实体与关系

- 实体：Game、Studio、Series、Tag（带类别：玩法 / 题材 / 氛围 / 其他）、PlayMode（每种模式一行：在线 / 同屏 / 局域网 / 远程同乐 × 合作 / 对抗，带人数上限）、PriceSnapshot（按 game × region 存储：币种、现价、原价、折扣、该区史低、快照时间、来源为每日快照或实时查询；各区互不覆盖）。
- 关系：DEVELOPED_BY、PUBLISHED_BY（游戏→工作室，按 IGDB 公司 ID）、IN_SERIES（游戏→系列）、HAS_TAG（游戏→标签，带票数、归一化权重与 is_core）、HAS_MODE（游戏→模式）、SIMILAR_TO（IGDB 相似游戏）、CO_LIKED（同好邻居：相似度与共同推荐人数）、HAS_PRICE（游戏→价格快照，按 region）。
- Game 另存游戏介绍：记录 AppID、语言、来源和更新时间，去除 BBCode / HTML 后生成文本向量；向量记录模型版本并与 AppID 对齐。介绍原文用于精排和推荐解释。
- 每条事实带来源、取数时间与状态（PASS / FAIL / UNKNOWN）；两源冲突时记 UNKNOWN 并保留两边原值。
- 落地方式：PostgreSQL 关系表 + 参数化 CTE 递归查询，不引入独立图数据库；同好邻居与向量矩阵另存为 NumPy 文件，启动时载入内存。

**不再使用的来源**：

- Steam appdetails：内容描述、年龄分级在批量接口里都有，且更结构化；它独有的配置要求不在判断范围内。
- SteamSpy：只用于首轮生成名单（已完成，7,425 款）；数据偏旧，以后重建名单改用 GetAppList + 批量接口取评价数。
- IGDB 的类型、主题、关键词：与 Steam 标签重复。
- Wikidata：唯一独有的是导演 / 设计师，全库约 770 款有记录，首版不用。
- FronkonGames 等离线档案数据集：本质是 appdetails + SteamSpy 的快照，被第 1 个来源覆盖。
- Kaggle “Steam Games Reviews 2024”（截至 2024-06）：评测者 ID 被取整成 16 的倍数，相邻账号混成一个；被第 5 个来源取代，已删除，不与新数据混用。
- Steam 商店“更多类似内容”页面：离线评估中预测效果比只推热门还差（见 5.5 同好通道），不采用。
- 其他公开评测数据集（2026-10 调研）：meownosaur/steam-17m-2years 覆盖到 2026-03、ID 完整，但许可证未知，确认前不用；其余多数每款只有 10~100 条评测，或 ID 同样被取整。
- PCGamingWiki：2026 年 8 月起 cargoquery 需 bot 登录，脚本请求被 Cloudflare 拦截；Co-Optimus：访问返回 403；ISteamApps/GetAppList：已下线。

**刷新与区域成本**：价格与史低每日刷新全库快照，请求时再对入围游戏实时查询（见 4.6“价格时效”）；标签、评价与模式每周刷新；评测数据截至 2026-10-13，定期增量补抓暂不考虑（2026-10-13 定）；以后补抓时，补抓后重算同好矩阵与时长参照分布。批量接口按 country_code 取价，每多一个区只多约 75 次请求。首批为 CN 与对照区 US，其他区按需拉取并缓存。

## 7. 评估方案

评估分两部分：大规模离线评估不需要人工标注，小规模请求集用于验证自然语言与端到端效果。

**离线评估（基于公开评测数据集）**：从同好通道的评测数据（第 5、6 个来源合并后）中，按评测者 ID 的哈希值切出 10% 作测试用户，同好矩阵与时长参照分布只用其余评测者计算，避免信息泄漏。测试用户与同好矩阵必须来自同一份数据，不与两份旧 Kaggle 数据混用。2026-10 最初的结果是在 Kaggle 2024 数据上跑的；换数据后已于 2026-10-13 重跑（结果见 5.5 同好通道与 10.5）。对每位测试用户，把其推荐过的游戏按时间分成“画像部分”和“留出部分”，用画像部分建多兴趣画像，看系统能否在 Top-K 中召回留出部分（Recall@K、NDCG@K）。场景二的群体评估用合成小组：从测试用户中按画像相似度组出喜好相近与差异较大的小组，一款推荐对某成员的“接受”定义为该成员在留出部分中推荐了它，由此计算全员接受率（做法参考 Baltrunas 等，RecSys 2010，该文也发现最优聚合方法随小组规模与成员相似度变化）。这部分样本量以千计，可支撑通道权重与 δ 等参数的调节。

**请求集**：计划 20~30 条真实或模拟的请求，实际用的是 32 条论坛真人求推荐帖（Reddit、PTT、知乎，两个场景各 16 条，见 7.1），兼作问题陈述的证据，主要检验需求理解、偏好原话匹配与开局卡。固定开发集与测试集，精排融合权重 w_r 这类只与原话有关的参数仅在开发集调节（通道权重与 δ 在离线评估上调，见下段）。多人用例保留逐人偏好标注，并包含成员喜好接近与差异较大的小组。价格用例固定首批区 CN，另设少量跨区用例验证区域参数化。

**样本量与调参**：请求集拆分后开发集只有十余条，只调精排融合权重 w_r 这类只与原话有关的参数；通道权重与 δ 在离线评估的开发用户上调节。方法之间在同一批用户或请求上做配对比较，报告 bootstrap 置信区间，不只报均值。离线评估的局限：留出部分代表“玩过并推荐”，不等于“今晚想玩”，因此结论以请求集的端到端结果作最终确认。

排序标注隐藏算法来源，采用统一候选标注池。群体算法对照固定候选池与个人分数表；召回实验固定知识库与请求，比较不同方法找回的相关游戏。

| 维度                         | 指标                                                    | 方法                                                                                                                         |
| ---------------------------- | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 意图理解                     | SessionSpec 槽位 Precision / Recall                     | 多语言口语（至少中英）、多轮修改、条件冲突                                                                                   |

**按模块比较，避免同时更换所有方法**：

1. **召回与个人打分**：标签 / 血统基线 → 加介绍向量 → 加同好通道与分数融合（RRF 作对照）→ 再加语义精排，在同一批 Top-N 上比较不精排、专用重排模型与 LLM 精排三种设置；比较相关性、召回覆盖与耗时。库画像另比较多兴趣画像与单一平均画像；多人另比较“平均画像召回”与“各成员候选并集”。
2. **群体聚合**：固定候选与归一化后的 UserScore，比较平均 + 最低分、Nash；先最低分再平均分为次要对照；另比较归一化前后的结果。以合成小组为主、请求集中的真实小组为确认，衡量群体接受度。
3. **最终排序**：固定候选、个人分与群体算法，比较全局加权 + MMR 与相关性窗口 + 窗口内调整 + MMR，再比较 MMR 前后的多样性。
4. **扩展备选**：PPR 与矩阵分解作为同好通道的对照，仅在完成上述核心实验后考虑，评估是否带来新增相关候选。

结论：有游戏库时，系统明显好于直接问 LLM，而直接问 LLM 与只推热门没有显著差别；LLM 在热门 100 款以外猜中的更多，两边名单互补。局限：这是同好通道的主场（无原话），与请求集（只有原话，LLM 占优）互为补充；只比了一个模型。

需求理解（系统理解对照逐帖条件）：人数 28/30，开局方式 9/9，预算金额与币种 32/32，说过玩过 / 排除的游戏召回 121/138（88%，漏的多是“GTA、Elder Scrolls”这类系列名对不到具体一款），能对上标签的雷区召回 15/17。

结论与局限：
- 守条件：系统 2 款、直接问 LLM 4 款，差距比 10-14 报告的“0 比 6”小得多，而且是在修掉一批读漏问题之后。系统的优势在于条件是逐条检查、写进卡片的（人数来源、谁要买、价格取数时间），查不到的进“待确认”，不会悄悄当作满足。
- 口味：精排是系统追上来的主要原因（第二评委 1.24 → 1.81），测试集上与直接问 LLM 只差 0.10；网友共识命中仍明显少（25 对 39），系统更常推荐不那么热门但合条件的游戏。
- 局限：样本小（测试集 16 条，评委打分的置信区间较宽，未算）；两个评委都是模型；原帖主反馈稀少，差异不显著。最终确认仍需人工按 0 / 1 / 2 标注（10.3）。

12. **2026-10-16 补齐的口径**（核对请求集时发现的问题和设计里原本没做的部分）：
    - 已玩过：用户说的“玩过 / 我们玩过 X”在多人请求里同样排除（之前只在单人时排除，r15 把帖子说玩过的《Terraria》排到了第 1）；Steam 时长只在单人时排除，多人常常愿意和朋友重玩。卡片上点过“不喜欢”的也排除。
    - 只有用户说要一个人玩（“单机”“singleplayer”“没朋友一起玩”，问卷里勾“一个人玩”）时，才要求游戏有 Steam“单人”分类（核心库 7,304 款中 6,731 款有），没有的判 FAIL。一个人来问不等于一个人玩：曾试过对所有单人请求都加这条，离线 hit@5 从 0.103 降到 0.095，因为留出玩家后来好评的游戏里 12.8% 是纯多人游戏（如 CS2、Apex），所以只在明说时启用（`SessionSpec.single_player`）。
    - 不在核心库的种子（如“像 PEAK 那样的”）：在全量轻量索引里按名字精确匹配（同名多款时取 Steam 评测最多的），实时取一次它的商店标签和介绍，作为只有内容信号的口味锚点（标签按核心库同样的 IDF 映射，介绍用同一个向量模型编码），没有同好数据，结果页写明（`outside.py`）。别名表的规范化先去掉 ™ / ® 再做 NFKC（之前 NFKC 把“™”变成“TM”，《HELLDIVERS™ 2》《DRAGON QUEST BUILDERS™ 2》等认不出），别名表已重建。Step 1 的提示词要求把游戏名写成英文官方商店名（如“文明帝國5”→ Sid Meier's Civilization V）。
    - 预算币种：Step 1 按原话记币种（CNY / USD / EUR / TWD……）。人民币、美元对应国区、美区；其他币种没有价格快照，不换算汇率，这次不按预算筛并在结果页说明（r15 的“20 欧元以内”之前被悄悄丢掉）。预算只和同币种的成员价格比较；团队总额只在全员同区时核对。
    - 跨区组队：谁买（远程同乐的主机、同屏机器上的购买者）只在同一区内比价，默认取排在前面的成员所在区，其他区的最便宜人选列为“其他方案”，由用户选。
    - IGDB 只有非 PC 版记录的人数（583 款；与 PC 版对照 96% 一致，3.1% 偏低且多为大型联机游戏）：请求人数不超过它时 PASS，超过时不判 FAIL，按 10.2 的补充规则继续，仍不能判断则 UNKNOWN（`player_counts.count_platform`）。多人游戏 2,288 款中 IGDB 有人数的 936 款，其中 394 款来自非 PC 记录。
    - 语义精排按目标分别打分：单人一列；多人时有自己原话的成员各一列、共同要求一列，一次 LLM 调用返回整张表，在群体聚合之前融合（`rerank.llm_scores` / `scoring.combine`）。
    - “没通过的”：结果页列出喜好分最高、但违反了某条硬条件（不含种子 / 已玩过）的至多 8 款及原因，喜好分在放宽到这些游戏的候选池上计算。
    - 慢循环（5.3 Step 6）：卡片上的“喜欢 / 不喜欢 / 玩过了”对绑定了 Steam 账号的成员存进 PostgreSQL（`member_feedback`），下次同一账号接入时生效：玩过 / 不喜欢排除，喜欢作为口味锚点，权重每 180 天减半。账号只存带密钥的哈希（密钥在 `.cache/`，不入库），访客的反馈只在会话内有效。“事实有误？”的报告存进 `fact_report`，不带任何账号或会话信息，只在下次数据刷新时人工对照。
    - PostgreSQL 进入请求路径：卡片的血统路径由递归 CTE 实时查询（`db.PathFinder`，5 款并发，超时 1.5 秒，失败回退内存中的同工作室 / 同系列）。
    - 标签分类：446 个标签由 LLM 一次性分为玩法 237、题材 101、氛围 39、其他 69（`scripts/build_tag_categories.py`，手工修正 5 处），存 `tag_categories.parquet`，载入为 `kb.tag_cat`。
    - 全量轻量索引：`IStoreService/GetAppList` 拉取商店里全部 193,457 款游戏的 AppID 与名称（`app_index.parquet`；只含仍在售的，核心库里已下架的 507 款不在其中），用于认出话里不在核心库的种子，以及在库摘要里列出不在核心库的游戏名。
    - 价格每日刷新：`playnext.refresh.refresh_prices`（CN、US 两区；Steam 批量接口每区 74 次请求，ITAD 查 ID 37 次、每区查史低 37 次，约 8 分钟），取数时间写进 parquet 元数据（不再用文件修改时间，之前重建表格会把 10-10 的价格显示成当天）；通过合理性检查（行数、有价比例、币种）才替换，旧文件备份。服务启动后由后台线程每小时检查，快照超过 1 天就刷新并热加载。2026-10-16 首次刷新：打折中的游戏从约 600 款升到约 1,100 款，约 920 款现价变化。`build_processed.py` 默认保留刷新过的快照。
