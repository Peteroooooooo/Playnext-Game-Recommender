离线 · 评测数据流水线

从 Steam 评测到“同好”信号

目标是拿到核心库每款游戏的全部评测（只要“谁推荐了什么”，不要正文），因为同好算法靠的是同一批人在不同游戏间的重合，抽样会把重合打散。现成的 Kaggle 数据集打底，缺的部分自己抓。

⛨

贯穿全程：隐私处理与测试玩家留出

fetch_reviews_increment.uhash

  • 加盐密钥哈希（BLAKE2b）
  • 按哈希固定留出测试玩家
处理
评测者 ID 读入内存后立刻换成加盐哈希，原始 ID 不落盘。Kaggle 和自抓的数据用同一个函数，所以同一个人在两边是同一个编号。按哈希固定划出一部分玩家作测试集，不参与任何建表，只用来离线评估。
1

抓取计划

fetch_reviews_increment.py plan

  • 按评测量切分时间段
输入
核心库名单；Steam 报的每款评测总数；Kaggle 已覆盖的时间范围
处理
判断每款缺哪段时间，按条数把时间段切成大小相近的任务
输出
抓取任务清单
2

并发抓取

fetch_reviews_increment.py run

  • 轮换出口代理池
  • 书签式翻页
  • 失败换节点重试
输入
任务清单
处理
Steam 按出口 IP 限速，所以每个连接换一个出口节点。同一时间段只能顺序翻页（下一页要用上一页的书签），并行只发生在时间段之间。超时、被拒、空页都换节点重问
输出
原始评测（已哈希，只留需要的列）
3

核对与修复

fetch_reviews_increment.py repair

  • 多节点多数投票计数
  • 逐级细分重抓（年 → 月 → 周 → 天 → 小时）
输入
已抓评测；Steam 报的条数
处理
每款问多次总数，取一致的结果作“应有多少”。数量不够的游戏把时间段逐级切小，每级只重抓对不上的那几段
输出
与 Steam 计数吻合的评测

Steam 在很长的时间段里翻页会中途断掉、假装“没有了”；个别节点还会报错误的条数。不核对就会悄悄缺数据。

4

补齐 Kaggle 的缺口

fill_kaggle_gaps.py measure / nonsteam / steam

  • 按购买类型分别计数比对
  • 同样的细分补抓
输入
Kaggle 现成评测；Steam 按“商店购买 / 非商店购买”分开报的条数
处理
Kaggle 只收了商店购买的评测，且部分游戏抓得不全。两类分别核对，缺的部分按第 3 步的方法补抓
输出
补齐后的两类评测

抽样比较两类评测的好评率和时长分布，看不出刷评，所以都保留，算法不区分购买方式。

5

合并去重

build_reviews_merged.py

  • 两遍流式处理
  • 按评测编号去重
  • 重叠部分交叉核对
输入
Kaggle 评测 + 自抓评测
处理
第一遍只读评测编号，决定每个文件保留哪些行；第二遍逐文件过滤写出，整表不进内存。两边都有的评测保留自抓的（更新），并逐条核对两边是否一致
输出
评测总表
6

建派生表

build_review_tables.py

  • EASE 物品协同（闭式解）
  • 共同推荐相似度
  • 时长分位分布
输入
评测总表（建表只用非测试玩家；同好只看好评）
处理
EASE：把“谁好评了什么”当成玩家 × 游戏矩阵，一次求解出“喜欢 A 的人会喜欢 B 多少”的权重。同好统计：每对游戏的共同好评人数与归一化相似度。时长参照：每款游戏玩家时长的分位分布
输出
同好权重矩阵（打分用）、同好统计（卡片证据用）、时长参照（读库画像用）、测试玩家评测（评估用）
7

离线评估与选型

eval_ease.py · playtime_signal.py

  • 时间切分留出
  • Recall@K + 置信区间
  • 去热门对照
输入
测试玩家的好评记录
处理
每人按时间前一半当口味、后一半当答案，比较“只推热门 / 余弦取最大 / 余弦相加 / EASE”谁猜中得多；再去掉最热门的游戏重比一次，排除“只是推了热门”
输出
选型结论：同好通道用 EASE；库画像用“时长分位”而不是绝对小时数
离线 · 游戏知识库

把多个公开数据源对齐成一份可查的事实库

按 Steam AppID 对齐，每个字段只认一个来源，不做多源投票。查不到的事实保持“未知”，不靠人工补录。

1

多源对齐

build_processed.py

  • 按 AppID 对齐
  • 单一来源原则
输入
Steam 商店批量接口（标签、分类、价格、介绍、语言、平台）；IGDB（人数上限、系列、开发商、相似游戏、通关时长）；IsThereAnyDeal（史低）
输出
游戏表、价格表、人数表、系列表
2

多人人数补全

build_processed.py · rules.py

  • 正则抽取
  • 补充规则
  • 来源可信度分级
处理
IGDB 没有人数时，从英文介绍里抽取明确写出的人数，再用规则补一部分。只来自主机版的人数只能让游戏“通过”，不能让它“不通过”
输出
能判断人数上限的多人游戏明显变多
3

游戏介绍向量

build_desc_embeddings.py · encoder.py

  • 多语言文本向量模型
处理
中英文介绍去格式后批量编码成向量，存成矩阵。请求时只需编码用户的一两句话
输出
介绍向量矩阵（介绍通道、偏好原话匹配用）
4

标签体系

kb.py · build_tag_categories.py

  • IDF 加权标签向量
  • 票数占比分核心 / 次要
  • LLM 一次性归类
处理
玩家标签按票数加权、冷门标签权重更高；票数占比高的算“核心标签”（雷区、玩法组合只认核心）。LLM 把全部标签归成玩法 / 题材 / 氛围 / 其他，结果入库
输出
标签向量、核心标签、标签分类
5

别名表

build_aliases.py · aliases.py

  • Unicode 规范化
  • LLM 补常用叫法
处理
中英文官方名、LLM 补充的俗称和缩写，统一规范化（去商标符号、全半角等）后建成“名字 → 游戏”的表
输出
别名表（需求理解时认游戏名）
6

口碑先验

kb.fit_beta_prior

  • 经验贝叶斯（Beta 先验）
处理
在全库的好评 / 差评数上拟合一个先验，把评测很少的游戏的好评率往全库平均拉
输出
平滑后的口碑分（排序时用）

只有几十条评测的 100% 好评，不该排在几万条评测的 95% 前面。

在线 · 一次推荐

所有请求走同一条主干，字段决定开哪些模块

单人和多人、一句话和问卷，进的是同一条流水线。多人时每个成员各算一份分数，最后再合成群体分。主干串联在 pipeline.py 的 Recommender.recommend。

0

输入

api.py · library.py · web/

  • 三种输入可叠加
  • Steam OpenID 登录
输入
一句话（“想要像 Hades 那样爽快的，100 块以内”）· 问卷（点选喜欢的游戏、感觉、雷区、预算）· Steam 库（登录后读已有游戏和时长）。多人时每位成员各有一份
输出
原始请求 + 表单 + 各成员的库
1

需求理解

understand.py · llm.py · aliases.py · outside.py · spec.py

  • LLM 结构化抽取
  • Pydantic 校验 + 失败重试
  • 别名匹配（精确优先）
输入
原话、问卷、库
处理
LLM 把原话转成固定字段：人数与开局方式、预算（带币种）、说过玩过 / 不要的游戏、雷区、想要和不想要的“感觉”（只能从 Steam 标签清单里选）、偏好原话。程序校验格式和取值，提到的游戏名用别名表认，核心库外的查全量索引。问卷不经过 LLM，直接转换
输出
SessionSpec：后面所有步骤共用的“需求单”

理解错了会传到后面每一步，所以这一步用强模型、严校验；LLM 不可用时退回只用问卷。

2

硬条件检查

rules.py

  • 三值逻辑 PASS / FAIL / UNKNOWN
  • 开局方式分流
  • 购买份数最低成本方案
输入
SessionSpec、事实库、价格快照
处理
逐款逐条检查：雷区、语言、平台、预算（只和同币种价格比）、玩过 / 排除。多人时再查官方模式分类、人数上限，按开局方式（在线 / 同屏 / 远程同乐 / 混合）算出每款最少要新买几份。查不到的事实记 UNKNOWN，不当成通过
输出
通过与待确认的游戏、每款的开局方案、“没通过的”及原因
玩法组合太严：同时满足的不够时，补上“一种核心、其余次要”的，排在后面并注明
全部不通过：冲突分析器找出放宽哪几条代价最小（子集和搜索），给出松绑建议
3

多路打分与语义精排

scoring.py · rerank.py · encoder.py

  • 多通道召回
  • 多锚点加权聚合
  • 池内归一化 + 加权融合
  • LLM 语义精排
  • 群体聚合
输入
通过的候选；口味锚点：种子游戏、Steam 库、以前点过喜欢的、核心库外的种子、偏好原话、感觉标签
输出
每款候选的相关性分（每位成员一份 + 共同要求一份，再合成），附打分依据

① 口味锚点怎么来

种子游戏用户说的“像 X 那样”
Steam 库按“比同款其他玩家玩得多的程度”（时长分位）给权重
以前喜欢的绑定账号点过的喜欢，随时间衰减
核心库外的种子只走标签和介绍两路

② 各通道独立打分（多个锚点的相似度加权求和）

同好喜欢锚点的人还喜欢什么EASE 权重
标签玩家标签是否相近IDF 加权余弦
介绍商店介绍讲的东西是否相近向量相似度
血统同开发商 / 同系列关系匹配
感觉想要的标签加分、不想要的减分标签加减分
偏好原话用户的一句话和介绍比向量相似度

③ 融合 → 精排 → 合成

归一化池内 min-max各通道分数先拉到同一尺度
融合加权求和按通道权重合成一个分
精排（有原话或感觉时）LLM 逐款打分取前若干候选，按原话 + 提到的游戏名打分，再与融合分按权重合并
群体（多人时）平均与最低分加权每人分数可比后合成，照顾最不满意的人

标签和介绍只看“长得像不像”，同好看“真实玩家会不会一起喜欢”，离线评估里同好最准，所以占主导；LLM 精排补上“原话里的细微要求”。

4

统一排序与重排

ranking.py · relax.py · pricing.py

  • 同系列折叠
  • 实时价格复核
  • 相关性窗口
  • MMR 多样性
输入
相关性分、通过名单、口碑分、价格
输出
精选 3~5 款 + 备选列表（可按价格筛、可展开同系列）+ 待确认

按顺序

折叠同系列只留最好的一款其余挂在它下面
入围取前若干款查实时价超预算的移出并说明
底线口碑太差的降级放进备选并标注
窗口喜好分相近的才比别的窗口内再看口碑、价格偏好、已拥有、短游戏
多样性MMR避免前几款彼此太像
完全不知道口味：按平滑口碑 × 评测数先排一版，并提示补一款喜欢的游戏

“喜好主导”：价格和口碑只能在喜好差不多的候选之间调顺序，不能让便宜但不对口味的游戏插到前面。

5

证据卡与推荐理由

cards.py · db.PathFinder

  • 证据汇集
  • 图谱递归路径
  • LLM 写理由 + 事实一致性校验
  • 模板兜底
输入
精选游戏、打分依据、事实库、价格
处理
每张卡收集：和种子的同好人数、共享的核心标签、种子到它的关系链（PostgreSQL 实时查）、现价与史低、人数和开局方案，每条都带来源。LLM 只根据这些事实写一段理由，程序检查理由里的数字和游戏名都能在卡片里找到，不符就重写一次，仍不符就用模板
输出
推荐卡（多人卡附开局方案和每人要不要买）
反馈闭环

只做“给用户要的”：反馈用来更准地满足用户说过的偏好，不做“换换口味”“给你惊喜”。

设计原则

调整框架时不要打破的几条

模型不定事实人数、模式、预算、价格只按数据判断，LLM 只理解和写字
未知不当通过查不到就标“需自行确认”，不偷偷放行
硬约束和软偏好分开雷区、人数、预算一票否决；风格、折扣只加分
喜好主导排序价格和口碑只在喜好相近的候选之间调整
多人先各算再合成先归一化每人分数，保留成员差异，照顾最不满意的人
无解不乱推没有符合的就给松绑建议，不偷换条件
